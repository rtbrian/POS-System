PART 2 - CONFIRMED INCONSISTENCIES TO LEARN FROM
=================================================

A. Frontend and backend error response mismatch
------------------------------------------------
Backend commonly returns { error: '...' }.
Register.tsx reads response.data.message.

Result:
The user often sees the generic message Registration failed instead of the real
validation or server error.

Fix to plan:
Choose one error contract, preferably:
{ error: { code: 'VALIDATION_ERROR', message: '...' } }
Update every controller and frontend service to use it consistently.

B. Database schema is not versioned
------------------------------------
No migrations or schema file was found.
The backend assumes users and products tables exist with specific columns.

Fix to plan:
Add database/migrations with numbered SQL migrations and a repeatable local setup.
Document how to create, migrate, seed, reset, and back up the database.

C. User model and SQL names disagree
-------------------------------------
backend/src/auth_services/models/user.model.ts expects:
- password_hash
- role_id
- business_id

backend/src/auth_services/services/auth.service.ts inserts:
- password
- role

JWT generation reads role_id and business_id.

Fix to plan:
Design the schema first, then make TypeScript interfaces, SQL queries, JWT claims,
and frontend types use the same names. Do not guess column names in code.

D. Database environment configuration is undocumented
-------------------------------------------------------
The backend reads DB_HOST, DB_USER, DB_PASSWORD, DB_NAME, DB_PORT, and JWT_SECRET,
but no committed .env.example was found.

docker-compose.yml defines local database values:
- user: postgres
- password: 12345
- database: pos_system
- port: 5432

Fix to plan:
Add backend/.env.example with placeholders and a documented local .env setup.
Never commit the real .env or production secrets.

E. Inventory routes are not protected
--------------------------------------
backend/src/inventory-service/routes/products.routes.ts exposes GET, POST, PUT,
and DELETE without verifyToken.

Result:
Unauthenticated users can potentially read and modify inventory.

Fix to plan:
Protect all product routes with authentication middleware and authorize each
operation using the authenticated user and business membership.

F. Business isolation is not implemented
------------------------------------------
Product creation hardcodes business_id: 1.
Product queries do not filter by the authenticated business.

Result:
Users from different businesses could see or change each other's products.

Fix to plan:
Put businessId in the verified token, obtain it from req.user, and include it in
every SELECT, INSERT, UPDATE, and DELETE condition.

G. Authentication is not enforced in frontend routes
-----------------------------------------------------
App.tsx defines dashboard, inventory, and POS routes without a protected route.

Result:
A user can navigate directly to private pages even without a token. Backend
protection must remain authoritative, but the frontend should also redirect for
a better user experience.

Fix to plan:
Add a ProtectedRoute component that checks token state and redirects to /login.
Also handle token expiry and logout globally.

H. Token lifetime and storage need a production decision
---------------------------------------------------------
JWT expires after 20 minutes and is stored in localStorage.

Risks:
- localStorage is exposed to JavaScript if an XSS vulnerability occurs.
- no refresh-token flow is implemented.
- the frontend does not visibly handle expiration.

Fix to plan:
For a production web app, evaluate short-lived access tokens plus secure,
httpOnly, sameSite refresh cookies. Add logout, rotation, expiry handling, and
revocation strategy.

I. Validation is incomplete and inconsistent
---------------------------------------------
Registration validates email format and password length, but product input
validation is only basic truthiness checking.

Fix to plan:
Use a shared validation library such as Zod on the backend. Validate numeric
ranges, non-negative stock, valid prices, string lengths, and allowed categories.
Return structured 400 responses.

J. Inventory API silently hides failures
-----------------------------------------
frontend/src/services/inventoryservice.ts returns [] from getProducts on any error.

Result:
The UI can display an empty inventory as if the business has no products, even
when the backend is down or access is denied.

Fix to plan:
Show a meaningful error state and preserve the distinction between an empty list,
401, 403, 404, and 500 responses.

K. Product update behavior is unsafe for nullable values
---------------------------------------------------------
The backend uses COALESCE for updates. This makes it impossible to intentionally
clear nullable category or description fields by sending null.

Fix to plan:
Use an explicit update DTO and decide whether omitted, null, and empty string have
different meanings.

L. Product ownership and delete behavior need verification
-----------------------------------------------------------
DELETE returns success without checking whether a row was actually deleted.

Fix to plan:
Use a business_id condition, check affected row count, and return 404 when the
product does not belong to the current business or does not exist.

M. Duplicate server entrypoints create confusion
-------------------------------------------------
There are separate auth_services/server.ts and inventory-service/server.ts files,
while backend/src/index.ts acts as a combined gateway. They use different ports and
CORS settings.

Fix to plan:
Choose one architecture for the first launch:
- one API process with clear route modules, or
- separately deployed services with explicit service boundaries.
For this first app, one API process is simpler and safer.

N. Production CORS is too broad and incomplete
-----------------------------------------------
The gateway allows any origin ending in .vercel.app.

Risks:
- unrelated preview deployments may call the API.
- the exact production frontend origin is not explicitly controlled.

Fix to plan:
Use an environment variable containing an exact comma-separated allowlist of
trusted origins. Keep localhost origins in development only.

O. HTTPS and proxy behavior are not addressed
----------------------------------------------
The current local setup uses HTTP and has no production reverse-proxy/security
configuration documented.

Fix to plan:
Deploy behind HTTPS, configure secure cookies if used, set trust proxy correctly,
and add helmet, rate limiting, request size limits, and secure headers.

P. No automated API or database tests are present
--------------------------------------------------
The repository currently has no visible test suite covering registration, login,
protected inventory, validation, or business isolation.

Fix to plan:
Add unit tests for services and integration tests for API routes using a test
database or isolated database container. Add frontend tests for form states and
API error handling.
